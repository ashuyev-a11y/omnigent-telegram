# omnigent-telegram

Telegram-бот — пульт управления оркестратором Omnigent. Один Telegram-чат
привязан к одному проекту (рабочей директории); бот запускает в нём
`omnigent run <bundle_path> -p "<текст задачи>"` и пересылает в чат
URL сессии и финальный вывод.

Это не интерфейс для сложного кодинга (для этого есть веб-UI Omnigent) —
только способ отдать короткую задачу с телефона и получить результат.

Этот README рассчитан на то, что вы разворачиваете бота с нуля на чистой
машине, без доступа к автору. Если что-то в нём разойдётся с реальным
поведением — читайте `bot.py`, `runner.py`, `config.py` и `SPEC.md`
(техзадание) — они первичны.

## Требования к окружению

Перед установкой на сервере должно быть:

- **Linux с systemd** (юнит из этого README рассчитан на systemd; на другой
  init-системе используйте эквивалентный механизм автозапуска).
- **Python 3.12** (`python3.12 --version`). Более старые 3.x могут работать,
  но проверялось и разрабатывалось на 3.12.
- **git** — для клонирования этого репозитория и репозиториев проектов,
  которыми будет управлять оркестратор.
- **`gh` (GitHub CLI), авторизованный** (`gh auth status`) — им пользуется
  сам оркестратор (агент Claude Code) внутри проектов, чтобы открывать PR.
  Бот его напрямую не вызывает, но без него оркестратор не сможет завершить
  свою обычную работу.
- **CLI `omnigent`, доступный в `PATH`**, и настроенный так, чтобы
  `omnigent run <bundle_path> -p "..."` отрабатывал вручную из терминала
  без дополнительных вопросов. Именно эту команду бот запускает в
  подпроцессе для каждого сообщения.
- **Claude Code CLI, установленный и авторизованный** на той же машине —
  бандл оркестратора (`bundle_path` в конфиге бота) по умолчанию использует
  Claude Code как имплементера. Проверьте `claude` (или ту команду, которой
  реально пользуется ваш бандл) до того, как подключать Telegram: если CLI
  не авторизован, все запуски `omnigent run` будут падать с ошибкой
  авторизации (см. Troubleshooting).
- Telegram-аккаунт с доступом к **@BotFather** для создания бота и токена.

Проверить готовность окружения одной командой перед началом:

```bash
python3.12 --version && git --version && gh auth status && omnigent --version && claude --version
```

Если любая из этих команд падает — почините её раньше, чем переходить к
шагам ниже; бот не компенсирует нерабочее окружение, он просто будет молча
или с ошибкой валить каждую задачу.

## Установка шаг за шагом

### 1. Склонируйте репозиторий бота

```bash
git clone https://github.com/ashuyev-a11y/omnigent-telegram.git
cd omnigent-telegram
```

### 2. Создайте venv и поставьте зависимости

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` ставит `python-telegram-bot`, `PyYAML` и `pytest` (нужен
только для тестов, в проде не используется рантаймом).

### 3. Убедитесь, что тесты проходят на чистом окружении

Тесты не требуют токена, сети или установленного Omnigent — подпроцесс в
`test_runner.py` подменяется, реальный `omnigent run` не вызывается. Это
самый быстрый способ убедиться, что venv и код в согласии до того, как вы
тронете systemd и реальный токен:

```bash
python -m pytest -q
```

Если тесты не проходят на чистой машине сразу после установки зависимостей —
дальше двигаться бессмысленно, сначала разберитесь с этим (см.
Troubleshooting или откройте issue).

### 4. Получите токен бота у @BotFather

1. Откройте Telegram, найдите `@BotFather`.
2. Отправьте `/newbot` и следуйте диалогу (имя, username, обязательно
   заканчивающийся на `bot`).
3. BotFather пришлёт токен вида `123456789:AAExampleTokenDoNotUseThisOne`.
   Это секрет уровня пароля — с ним можно полностью управлять ботом.

### 5. Сохраните токен правильно

**Токен никогда не хранится в `config.yaml` и никогда не передаётся
аргументом командной строки.** Код (`config.py`) читает его исключительно
из переменной окружения `TELEGRAM_BOT_TOKEN` и осознанно не поддерживает
других источников.

Рекомендуемый способ на сервере — отдельный env-файл с правами `600`,
читаемый только владельцем:

```bash
cat > /home/deploy/omnigent-workspaces/telegram-bot/telegram-bot.env <<'EOF'
TELEGRAM_BOT_TOKEN=123456789:AAExampleTokenDoNotUseThisOne
EOF
chmod 600 /home/deploy/omnigent-workspaces/telegram-bot/telegram-bot.env
```

Проверьте права:

```bash
ls -l telegram-bot.env
# -rw------- 1 deploy deploy ... telegram-bot.env
```

Этот файл **не коммитится** (он не должен лежать внутри git-репозитория
вообще, либо должен быть в `.gitignore` — в этом репозитории `.env` уже
исключён). При ручном локальном запуске (не через systemd) токен просто
экспортируется в текущем шелле: `export TELEGRAM_BOT_TOKEN="..."` — этот
способ годится для разовой проверки, но не для постоянной службы, потому
что переменная теряется при перезапуске шелла.

### 6. Узнайте свой chat_id и user_id

Прежде всего:

1. Добавьте бота в нужный чат (личку, группу или канал) или просто напишите
   ему в личные сообщения.
2. Отправьте туда любое сообщение (например, боту в личку или в группу, где
   он состоит).
3. Запросите обновления через Bot API (токен уже должен быть в переменной
   окружения из шага 5):

   ```bash
   curl "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getUpdates"
   ```

4. В ответе найдите `message.chat.id` — это и есть искомый `chat_id` (для
   групп он отрицательный, например `-1001234567890`). Там же
   `message.from.id` — это ваш `user_id`.

Если `getUpdates` вернул пустой список `result`, значит сообщение до бота
не дошло (проверьте, что писали именно тому боту и что бот ещё ни разу не
запускался в режиме long polling — см. Troubleshooting про конфликт
`getUpdates`) или что в группе у бота включена приватность (см. раздел про
второй проект ниже).

Свой `user_id` можно узнать и без curl — написав любому публичному боту
вида `@userinfobot`.

### 7. Заполните config.yaml

Скопируйте пример и отредактируйте под себя:

```bash
cp config.example.yaml config.yaml
```

```yaml
bundle_path: /home/deploy/omnigent-agents/orchestrator
timeout_seconds: 1800
state_file: ./state.json

projects:
  - name: orchestrator
    chat_id: -1001234567890
    workdir: /home/deploy/omnigent-workspaces/orchestrator-repo
    allowed_user_ids: [123456789]
```

Пояснение по каждому полю:

- **`bundle_path`** (обязательно) — путь к бандлу оркестратора, который
  `omnigent run` будет запускать для *всех* проектов. Один бандл на всего
  бота; отличаются только рабочие директории и допущенные чаты/пользователи.
- **`timeout_seconds`** (обязательно) — сколько секунд ждать завершения
  одного запуска `omnigent run`, прежде чем бот убьёт подпроцесс и сообщит
  в чат о таймауте. Берите с запасом относительно самой долгой ожидаемой
  задачи — по умолчанию в примере это 1800 (30 минут).
- **`state_file`** (опционально, по умолчанию `./state.json`) — путь к
  JSON-файлу, в котором бот хранит id последней omnigent-сессии для каждого
  чата, чтобы продолжать диалог между сообщениями, а не начинать новую
  сессию с чистого листа каждый раз. Запись атомарная (сначала во временный
  файл рядом, затем `os.replace()` поверх него), так что падение процесса
  посреди записи никогда не оставит файл состояния битым. Этот файл — не
  секрет с точки зрения текста, но в нём накапливаются служебные id;
  держите его вне git (в `.gitignore` уже есть).
- **`projects`** (обязательно, непустой список) — список привязок
  чат → проект. Каждый элемент:
  - **`name`** — произвольное читаемое имя проекта, используется в ответе
    на `/start`.
  - **`chat_id`** — id Telegram-чата, привязанного к этому проекту (см.
    шаг 6). Должен быть уникален в пределах конфига — дубликат `chat_id`
    роняет бота при старте с понятной ошибкой валидации.
  - **`workdir`** — рабочая директория, в которой запускается
    `omnigent run` для этого чата (обычно — корень git-репозитория
    соответствующего проекта; см. подготовку рабочей директории ниже).
  - **`allowed_user_ids`** — непустой список Telegram `user_id`,
    которым разрешено писать боту в этом чате. Сообщения от всех
    остальных пользователей и из всех остальных чатов **игнорируются без
    какого-либо ответа** — это осознанное поведение, а не баг (см.
    Troubleshooting).

`config.yaml` и `state.json` — в `.gitignore`. Не коммитьте их: в них
реальные пути, id чатов и идентификаторы сессий.

По умолчанию бот ищет `./config.yaml` в рабочей директории процесса. Другой
путь можно задать переменной окружения `OMNIGENT_TG_CONFIG`.

### 8. Подготовьте рабочую директорию для каждого проекта

`workdir` из `config.yaml` — это обычный git-репозиторий, в котором
`omnigent run` будет реально работать (читать код, коммитить, открывать
PR через `gh`). Подготовьте его так же, как готовили бы для ручной работы:

```bash
git clone https://github.com/<org>/<project-repo>.git \
  /home/deploy/omnigent-workspaces/orchestrator-repo
cd /home/deploy/omnigent-workspaces/orchestrator-repo

# окружение для тестов и линтов этого проекта — то, чем реально будет
# пользоваться оркестратор при проверке своей работы, например:
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
# или npm ci / poetry install / go mod download — смотря что за проект
```

Убедитесь, что от имени пользователя, под которым будет работать systemd-
служба (в этом README — `deploy`), можно:

- писать в `workdir` и коммитить в нём (`git config user.name` /
  `user.email` настроены, `git push` работает — то есть либо ssh-ключ, либо
  сохранённые https-креды этого пользователя);
- запускать `gh` из этой директории без интерактивного логина (`gh auth
  status` возвращает успех для того же пользователя ОС);
- запускать тестовый/линт-гейт проекта той же командой, которой пользуется
  оркестратор, чтобы задачи не проваливались на первом же шаге проверки.

Один и тот же `bundle_path` подходит для любого числа проектов — под
каждый новый проект нужен только новый `workdir` и новая запись в
`projects`.

### 9. systemd-юнит для автозапуска

Пример `/etc/systemd/system/omnigent-telegram.service`:

```ini
[Unit]
Description=omnigent-telegram bot
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/home/deploy/omnigent-workspaces/telegram-bot
Environment=OMNIGENT_TG_CONFIG=/home/deploy/omnigent-workspaces/telegram-bot/config.yaml
EnvironmentFile=/home/deploy/omnigent-workspaces/telegram-bot/telegram-bot.env
ExecStart=/home/deploy/omnigent-workspaces/telegram-bot/.venv/bin/python bot.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Ключевые моменты:

- `EnvironmentFile` подключает `telegram-bot.env` (шаг 5, права `600`) —
  токен так и не попадает ни в сам юнит-файл, ни в вывод `systemctl
  status`/`ps`.
- `Restart=on-failure` + `RestartSec=5` — служба сама поднимется после
  падения процесса (например, после сетевого сбоя), но не будет пытаться
  бесконечно быстро рестартовать при постоянной ошибке конфигурации.
- `User=deploy` — служба обязана работать от того же пользователя ОС, под
  которым вы готовили `workdir`, ssh-ключи и `gh auth login` на шаге 8:
  systemd по умолчанию не наследует ваше пользовательское окружение.

Включение и первый запуск:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omnigent-telegram.service
```

### 10. Управление службой и просмотр логов

```bash
sudo systemctl status omnigent-telegram.service     # текущее состояние
sudo systemctl restart omnigent-telegram.service    # перезапуск
sudo systemctl stop omnigent-telegram.service        # остановка
sudo journalctl -u omnigent-telegram.service -f      # логи в реальном времени
sudo journalctl -u omnigent-telegram.service -n 200  # последние 200 строк
```

Бот логирует факт запуска задачи, `chat_id`, код возврата и длительность
выполнения. Текст задачи целиком и переменные окружения в логи не попадают.

### 11. Обновление

```bash
cd /home/deploy/omnigent-workspaces/telegram-bot
git pull
source .venv/bin/activate
pip install -r requirements.txt   # если requirements.txt изменился
sudo systemctl restart omnigent-telegram.service
```

После рестарта проверьте `sudo systemctl status` и хвост логов — если
`config.yaml` в этот момент рассинхронизировался с новым кодом (например,
появилось новое обязательное поле), бот упадёт при старте с понятной
ошибкой валидации из `config.py`.

## Команды бота

- `/start` — краткая справка и имя проекта, привязанного к чату.
- `/status` — выполняется ли сейчас задача в этом чате и URL её сессии;
  если задача не выполняется, показывает id продолжаемой сессии (если она
  есть) либо сообщает, что следующее сообщение начнёт новый разговор.
- `/cancel` — прервать текущую задачу этого чата.
- `/new` — сбросить сохранённую сессию чата: следующее сообщение начнёт
  разговор с чистого листа вместо продолжения предыдущего.

Обычное текстовое сообщение (без команды) в известном чате от разрешённого
пользователя запускает новую задачу — если в чате уже что-то выполняется,
бот ответит, что занят, со ссылкой на текущую сессию.

Такое сообщение продолжает предыдущую omnigent-сессию этого чата
(`omnigent run ... --resume <id>`), а не запускается с чистого листа каждый
раз — id сессии сохраняется в `state_file` после каждого успешно принятого
запуска. Если продолжение не удалось (сессия устарела или была удалена на
сервере — ненулевой код возврата не по причине таймаута или отмены), бот сам
сбрасывает сохранённую сессию, сообщает об этом в чат и просит повторить
задачу; повторная отправка начнёт новую сессию.

## Тесты

```bash
python -m pytest -q
```

Тесты не требуют токена, сети или установленного Omnigent — подпроцесс в

## Troubleshooting

### Бот молчит на сообщение из конкретного чата

Это ожидаемое поведение, а не баг. Бот отвечает **только** в чатах,
перечисленных в `projects[].chat_id`, и только пользователям из
соответствующего `allowed_user_ids`. Сообщение из любого другого чата или
от любого другого пользователя игнорируется полностью — бот не присылает
даже сообщение об отказе (сделано намеренно, чтобы не подтверждать
существование и логику бота посторонним).

Если бот не отвечает там, где должен:

1. Проверьте `getUpdates`, чтобы получить фактический `message.chat.id` и
   `message.from.id` сообщения, которое не обработалось (см. шаг 6
   установки), и сверьте их буквально с `config.yaml`.
2. Помните, что `chat_id` группы — отрицательное число; если в конфиге
   случайно оказалось положительное значение того же id, совпадения не
   будет.
3. Убедитесь, что читаете актуальный конфиг: `OMNIGENT_TG_CONFIG` может
   указывать не туда, куда вы редактируете (`systemctl cat
   omnigent-telegram.service` покажет, какой путь реально подставлен через
   `Environment=`).
4. После правки `config.yaml` перезапустите службу — конфиг читается один
   раз при старте процесса, hot-reload не предусмотрен.

### `Conflict: terminated by other getUpdates request`

Telegram Bot API разрешает только один активный long-polling запрос
`getUpdates` на токен одновременно. Эта ошибка означает, что где-то
одновременно с systemd-службой запущен второй процесс с тем же токеном —
например, вы вручную запустили `python bot.py` в терминале для отладки,
забыв, что systemd-служба уже работает, либо служба запущена сразу на двух
серверах с одним и тем же `telegram-bot.env`.

Решение: убедитесь, что процесс с этим токеном ровно один.

```bash
sudo systemctl status omnigent-telegram.service   # служба точно одна?
ps aux | grep '[b]ot.py'                          # нет ли осиротевшего ручного запуска?
```

Остановите лишний процесс (`kill <pid>` для ручного запуска или
`sudo systemctl stop` на лишнем сервере) и перезапустите единственный
оставшийся.

### `401 Authentication required` от omnigent

Это ошибка не Telegram, а самого `omnigent run`: авторизация CLI на
сервере слетела (истекла сессия/токен провайдера модели, привязанного к
CLI). Симптом в чате — задача падает почти сразу, `/status` показывает
ненулевой код возврата, а в `stderr_text` (последние строки видно в ответе
бота) — текст про authentication required.

Решение — переавторизовать `omnigent`/провайдера модели на той же машине и
под тем же пользователем ОС (`User=` из systemd-юнита), под которым
работает служба, тем же способом, каким авторизовывали при первичной
настройке. После переавторизации `sudo systemctl restart
omnigent-telegram.service` не обязателен (бот сам просто перезапускает
подпроцесс `omnigent run` на следующем сообщении), но полезен, чтобы
исключить залипшее состояние.

### Лимиты модели исчерпаны

Если провайдер модели, стоящий за `omnigent`/Claude Code, исчерпал квоту
или упёрся в rate limit, `omnigent run` завершится с ошибкой или зависнет
до таймаута `timeout_seconds`, а не выдаст осмысленный результат. Бот в
этом случае честно перешлёт то, что вернул подпроцесс (хвост stderr) или
сообщит о таймауте — сам он лимиты не отслеживает и не ретраит.

Что делать: проверить у провайдера остаток квоты/лимитов тем же способом,
каким проверяли бы это при ручном запуске `omnigent`/`claude` из терминала
на этом сервере, и либо подождать сброса окна лимита, либо поднять план.
Пока лимит не восстановлен, повторные сообщения в бота будут проваливаться
тем же образом — это не повод перезапускать службу.

### URL сессии не приходит в чат, хотя задача явно выполняется

`omnigent run` печатает свои служебные строки, включая строку
`Omnigent session: <url>`, в **stderr**, а не в stdout (stdout несёт
только финальный ответ агента). Бот (`runner.py`) ищет URL сессии именно в
первых строках stderr. Если вы форкаете этот код или меняете способ
запуска оркестратора — не переносите разбор URL на stdout, иначе строка
никогда не найдётся и `/status` перестанет показывать ссылку на сессию.
Если после такого изменения URL пропал — сравните, во что реально пишет
`Omnigent session:` ваша версия `omnigent run` (`omnigent run <bundle_path>
-p "test" 2>&1 1>/dev/null` покажет только stderr) с тем, что ожидает
`extract_session_url()` в `runner.py`.

## Подключение второго (и последующего) проекта

Один бот и один процесс полностью обслуживают произвольное число проектов
— каждый со своим Telegram-чатом. Чтобы добавить ещё один:

1. **Склонируйте репозиторий проекта** в отдельную рабочую директорию и
   подготовьте её так же, как в шаге 8 установки (venv/зависимости, ssh-
   ключ или https-креды для `git push`, рабочий `gh auth status` от имени
   того же пользователя ОС, что запускает службу):

   ```bash
   git clone https://github.com/<org>/<second-project>.git \
     /home/deploy/omnigent-workspaces/second-project
   ```

2. **Заведите отдельный Telegram-чат под этот проект.** Проще всего —
   создать новую группу в Telegram и добавить в неё бота: тогда у неё будет
   свой уникальный (отрицательный) `chat_id`, отдельный от чата первого
   проекта, и не нужно заводить второго бота. Узнайте `chat_id` этой группы
   тем же способом, что в шаге 6 (напишите в группу и посмотрите
   `getUpdates`).

3. **Отключите приватность бота у @BotFather**, если бот будет состоять в
   группе (а не только в личных чатах): по умолчанию боты в группах Telegram
   получают через Bot API только сообщения, начинающиеся с `/команды` или
   явно адресованные боту (реплай/упоминание) — обычный текст мимо них
   проходит незамеченным, и `getUpdates` не покажет `message.chat.id` для
   таких сообщений вообще. Чтобы бот видел все сообщения в группе:

   - откройте `@BotFather` → `/mybots` → выберите бота →
     `Bot Settings` → `Group Privacy` → `Turn off`;
   - если бот уже был в группе на момент включения/выключения приватности,
     удалите его из группы и добавьте заново — Telegram применяет новый
     режим только к боту, добавленному после смены настройки.

4. **Добавьте вторую запись в `projects`** в `config.yaml`:

   ```yaml
   projects:
     - name: orchestrator
       chat_id: -1001234567890
       workdir: /home/deploy/omnigent-workspaces/orchestrator-repo
       allowed_user_ids: [123456789]

     - name: second-project
       chat_id: -1009876543210
       workdir: /home/deploy/omnigent-workspaces/second-project
       allowed_user_ids: [123456789]
   ```

   `bundle_path` и `timeout_seconds` — общие для всех проектов, повторять
   их не нужно. `chat_id` каждой новой записи обязан быть уникален во всём
   файле — дубликат уронит бота при старте.

5. **Перезапустите службу**, чтобы она подхватила новый конфиг:

   ```bash
   sudo systemctl restart omnigent-telegram.service
   ```

6. Напишите что-нибудь простое (например, `/start`) в новом чате и
   убедитесь, что бот ответил именем `second-project` — это подтверждает,
   что `chat_id` сопоставился верно.

## Ограничения этой версии

Нет approval-карточек и кнопок, нет параллельных задач в одном чате, нет
доступа к Supabase/Vercel/ключам проектов, нет автоматического определения
проекта по тексту, нет вебхуков (только long polling).
